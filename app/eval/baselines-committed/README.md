# Committed eval baselines (issue #525)

Version-controlled last-known-good scorecards, one JSON file per `scenarioId__variant`, in the same
shape as `eval/runner/baseline.ts`'s `Scorecard`. This is **not** the gitignored `eval/baselines/`
directory (that one is the developer's local ad-hoc tweak-and-compare store, per SPEC-0042 EVAL-8) —
this directory is what the nightly CI **eval scorecard** job (`.github/workflows/nightly.yml`) diffs
against, so a quality regression is a repo-visible signal instead of something only one machine ever saw.

## Why it starts empty

Populating it for real requires a live BYOA `copilot` run (`KB_EVAL=1`, scoped eval creds) against
every scenario in `eval/scenarios/`. That can't be produced by a static code change — it has to come
from an actual run, the same way the e2e visual-snapshot baselines (`*-linux.png`) are only ever
regenerated by a dispatch, never hand-authored. Until the first promotion run, every check here is
`new` (not a regression) — see `diffScorecards` in `../runner/baseline.ts`.

## How it gets populated / refreshed

Dispatch the nightly workflow with `update_eval_baseline: true` (or wait for a scheduled run once the
harness is trusted). That run:

1. Executes `KB_EVAL=1 KB_EVAL_UPDATE_BASELINE=1 npm run eval:scorecard` — every scenario × variant,
   scored, saved into this directory (`COMMITTED_BASELINE_DIR`).
2. Commits the refreshed JSON files back to the branch (mirrors the `update_snapshots` dispatch path
   in `ci.yml`'s `snapshots` job).

A routine (non-dispatch) nightly/weekly run only **diffs** against what's here — it never overwrites it.
